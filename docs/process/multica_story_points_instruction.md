# Инструкция Multica: оценка задач в story points

Статус: переносимая версия канонического контракта FantasyDisk.

Эта инструкция **заменяет** attachment
`multica_story_points_efficiency_instruction.md` (ID
`019f6726-716b-7489-9cf2-f9551eeec316`), приложенный к FAN-1126. Старый файл
не следует использовать для новых оценок или отчётов: он задаёт несовместимую
формулу. Источник истины остаётся
[`story_points.md`](story_points.md); при расхождении побеждает он.

## Модель

Для любой новой или существенно изменяемой actionable issue применяется
относительная модель CUE:

- **Complexity** — сложность решения и число взаимодействующих систем;
- **Uncertainty** — неизвестность, риск, внешние зависимости и неоднозначность;
- **Effort** — полный объём реализации, документации, тестов, QA и cleanup.

CUE не складывается по формуле. Факторы рассматривают вместе и выбирают
ближайший подходящий относительный размер; между двумя значениями выбирают
большее до уточнения или декомпозиции. Нельзя ставить каждому фактору баллы,
механически складывать C, U и E или переводить результат через пороговую таблицу.

Единственная шкала: **`1, 2, 3, 5, 8, 13`**.

| SP | Ориентир |
| --- | --- |
| `1` | Полностью понятная локальная правка с простой проверкой. |
| `2` | Небольшая известная задача с несколькими связанными изменениями. |
| `3` | Bounded-задача с несколькими файлами или одной заметной неизвестностью. |
| `5` | Существенный подсистемный результат с edge cases и заметным QA. |
| `8` | Большая cross-system/cross-role работа с широким регрессом. |
| `13` | Очень большой единый результат с высоким интеграционным риском. |

Задача больше `13 SP` не является executable: её разбивают на independently
testable child issues. Даже для `13 SP` декомпозиция предпочтительна, если есть
чистые границы результатов.

## Обязательная запись и readiness

До assignment, dispatch или `in_progress` description содержит:

```md
## Оценка сложности

Story points: 5
Label: `SP:5`
Модель: CUE / Fibonacci `1, 2, 3, 5, 8, 13`
Обоснование: <complexity, uncertainty и полный effort до готового результата>
```

На issue должен быть ровно один канонический Label `SP:<N>` из `SP:1`, `SP:2`,
`SP:3`, `SP:5`, `SP:8`, `SP:13`. Metadata обязана содержать совпадающие
`story_points=<N>` и `estimation_model="CUE Fibonacci 1,2,3,5,8,13"`.
Description, Label и metadata проверяются dispatcher и worker повторно; любое
расхождение, отсутствие оценки или размер выше `13 SP` возвращаются PM на
уточнение или декомпозицию. Это правило также действует для QA, bug,
improvement и handoff children.

При существенном изменении scope до продолжения работы заменяют старый Label,
обновляют description и metadata, затем фиксируют в Multica comment старую и
новую оценку с причиной. Обычный ход реализации не является поводом подгонять
SP задним числом.

## Отчёты и переход

Отчёты описывают только поток команды и процесса: выполненные SP за период,
cycle time по `SP:<N>`, first-pass QA/rework, возраст WIP и план/факт scope.
Нельзя переводить SP в часы, ранжировать людей, агентов или роли по SP либо
выдавать относительный размер за персональный KPI.

Новые issues получают запись сразу; существующие `backlog`/`todo` — до
следующего dispatch; `in_progress`/`in_review` — при ближайшем содержательном
обновлении. Исторические `done`, `cancelled` и Jira Archive массово не
переоцениваются.
