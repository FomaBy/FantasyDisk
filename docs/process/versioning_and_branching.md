# Versioning And Branching Policy

Обновлено: 2026-06-14

## Текущее Правило

FantasyDisk переходит на версионность:

- `main` - стабильная линия версии `0.1`;
- `dev` - активная рабочая ветка текущей линии `0.1.x`;
- текущая разработка: стабилизация `0.1.5` в `Спринт 0.1.5` с feature block,
  включённым 2026-06-14.

## Feature Block — активен для 0.1.5

Feature freeze `0.1.4` был снят 2026-06-13 после релиза `v0.1.4`, но новый
feature block 0.1.5 включён директивой пользователя 2026-06-14. В текущем
релизе доделываются только уже заведённые board-задачи 0.1.5, bug/QA defects,
regressions и release blockers. Новые не-баговые задачи получают
`Версия: 0.1.6`, остаются в backlog/fixVersion 0.1.6 и не добавляются в активный
спринт 0.1.5.

## Branch Ownership

| Branch | Назначение | Правило |
| --- | --- | --- |
| `main` | Стабильная версия `0.1` | Не вести обычную разработку напрямую |
| `dev` | Активная рабочая ветка `0.1.x` | Стабилизация `0.1.5`; работать по task board/Jira, новые фичи — в `0.1.6` backlog |

## Правила Для Агентов

Перед началом любой задачи агент должен проверить текущую ветку:

```bash
git branch --show-current
```

Ожидаемая ветка для разработки:

```text
dev
```

Если агент находится на `main`:

- не начинать разработку в `main`;
- переключиться на `dev`, если это безопасно;
- если есть незакоммиченные изменения и переключение рискованно, остановиться и явно описать ситуацию.

Если ветки `dev` нет:

- создать `dev` от актуального `main`, если это безопасно и соответствует задаче;
- зафиксировать действие в финальном ответе.

## Release Flow

Текущий ожидаемый flow:

1. `main` хранит `0.1`.
2. `dev` используется для стабилизации текущей версии `0.1.5`.
3. Активные задачи `0.1.5`, баги и release blockers закрываются в текущем
   sprint; новые не-баговые задачи во время текущего feature block уходят в
   `0.1.6`.
4. После проверки `dev` можно будет слить в `main` как новую стабильную версию.
5. После релиза документация должна быть обновлена и отражать новую стабильную версию.

## Документация Версий

Документы должны явно понимать текущую линию разработки:

- `docs/design/current_game_state.md` описывает активное состояние `dev`, если не указано иначе.
- `docs/tasks/*.md` по умолчанию создаются для `dev`.
- release/finalization tasks должны явно указывать, какую версию готовят.

## Запреты

- Не коммитить `.godot/`.
- Не делать обычные feature changes напрямую в `main`.
- Не переносить изменения между `main` и `dev` destructive-командами без явного запроса.
- Не делать `git reset --hard`, `git checkout -- <file>` или похожие destructive operations без явного разрешения.

- `dev` используется для стабилизации `0.1.5`; feature block направляет новые
