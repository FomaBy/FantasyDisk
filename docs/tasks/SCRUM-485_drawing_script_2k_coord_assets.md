# SCRUM-485: Рисующий скрипт: генерация UI-ассетов по координатам @2K

Jira: SCRUM-485 · Роль: backend · Контур: integration · Приоритет: P1 · foma · Эпик: SCRUM-481 (UI Overhaul 2K)
Статус: К выполнению

## Что и зачем

**Цель (продукт/игрок).** В рамках глобального редизайна UI на базу 2K (2560×1440)
SCRUM-484 уже зафиксировал точные координаты слотов контента `x,y,w,h` для блока
Меню/Навигация (8 экранов) как именованные `*_2K`-константы в `scripts/ui_screens.gd`.
Сейчас все эти слоты (модалки, панели, кнопки) рисуются ОДНИМ исходным PNG-ассетом
рамки (`minimal_metal`), который растягивается/тайлится 9-slice'ом под совершенно
разные размеры слотов. При сильном расхождении пропорций слота и исходника орнамент
(уголки, бордюр, акценты) едет: углы расплываются, толщина рамки скачет, акцентные
«L-скобки» искажаются.

**Что нужно.** Рисующий (генерирующий) Python-скрипт, который БЕРЁТ координатную
спеку @2K (`*_PANEL_2K` и родственные `Rect2`-константы) как ВХОД и выдаёт frame/
panel/button-ассеты ровно в нужный пиксельный размер слота, так чтобы:
- центр (плоская середина) тянулся 9-slice'ом, а орнамент по краям рисовался в свой
  натуральный размер и НЕ искажался;
- для каждого слота генерился ассет под его реальные w×h (или класс размеров), а не
  один универсальный исходник на всё;
- результат проходил рендер-верификатор (проверка размеров/9-slice/безопасной зоны).

**Ожидаемый результат.** Воспроизводимый пайплайн `координаты-константы → скрипт →
ассеты → интеграция`: запустил скрипт — получил набор PNG точного размера + контактный
лист-превью + verdict верификатора (PASS/FAIL по каждому ассету). Это разблокирует
остальные блоки эпика (выбор героя/оружия, бой/HUD, экономика, кодекс, исходы).

### Как ассеты потребляются в рантайме (важно для корректного 9-slice)
- `scripts/ui/ui_theme_paths.gd` — `class_name UIThemePaths`. Канонические пути ассетов
  активной темы `minimal_metal` + калибровка 9-slice:
  - `MINIMAL_METAL_FRAME_PATHS` (47–54): пути к 6 типам рамок (`modal/panel/card/tooltip/hud_strip/field`).
  - `MINIMAL_METAL_FRAME_SOURCE_SIZE` (55–62): натуральный размер исходного PNG.
  - `MINIMAL_METAL_FRAME_TEXTURE_MARGINS` (63–70): **бордюры 9-slice (left,top,right,bottom)**.
  - `MINIMAL_METAL_FRAME_CONTENT` (71–78): content-margins (внутренний инсет под текст).
  - `MINIMAL_METAL_FRAME_SAFE_RECTS` (79–86): safe-area внутри рамки.
- Реальные PNG: `assets/sprites/ui/frames/minimal_metal/ui_frame_minimal_metal_*.png`.
  Их пиксельный размер ТОЧНО совпадает с `MINIMAL_METAL_FRAME_SOURCE_SIZE`
  (проверено: modal 986×900, panel 782×716, card 426×486, tooltip 760×242,
  hud_strip 1122×288, field 616×286).
- `scripts/ui_screens.gd:_global_texture_style()` (7483–7510): строит `StyleBoxTexture`
  с `texture_margin_*` из margins и `axis_stretch_*  = AXIS_STRETCH_MODE_TILE` (тайл краёв,
  тянется только центр). Это и есть рантайм-9-slice.
- `_scaled_frame_margins()` (7023–7030) и `_scaled_frame_margins_xy()` (7033–7041):
  скейлят бордюры под фактический `display_size`. `_xy` — раздельно по X/Y (вот тут и
  плывёт орнамент, когда aspect слота != aspect исходника).

### Текущие «рисующие» скрипты (база для обобщения)
- `tools/render_bright_frames.py` — **самый близкий прототип**: функция `render(w, h)`
  рисует 9-slice-safe рамку (полупрозрачная заливка-градиент + бордюр + угловые
  L-скобки, держащиеся ВНУТРИ margin-полосы, чтобы при тайле центра углы оставались
  чёткими). Сейчас гоняется по уже существующим PNG, беря их `w,h` из файла, и
  перерисовывает in-place (размеры сохраняются). НЕ читает `*_2K`-координаты.
- `tools/render_bright_buttons.py` — то же для кнопок.
- `tools/build_ornate_ui_frame_kit.py`, `build_*_ui_kit.py` — слайсят рамки из готового
  спрайт-листа по хардкод-боксам (`crop` + flood-alpha), не из координатной спеки.
- `tools/generate_ui_overhaul_visual_assets.py:draw_frame(path, size, ...)` — процедурный
  генератор рамки под произвольный `size` (но помечен SUPERSEDED для frames/icons).
- `tools/sprite_quality_audit.py` — аудит PNG на артефакты (stray-острова, спеки, гало);
  можно переиспользовать как часть верификатора.

Вывод: примитив «нарисовать 9-slice-safe рамку в w×h» уже есть (`render(w,h)`), но нет
звена «прочитать `*_2K` слоты → прогнать их через рисовалку → разложить по ассетам →
верифицировать». Его и надо построить.

## Что сделать — по шагам

1. **Создать `tools/build_ui_2k_frame_kit.py`** (новый, отдельный — НЕ трогать рантайм-`.gd`).
   Скрипт = пайплайн `координаты → ассеты`:
   - **Источник координат.** Завести модуль-парсер: вытащить `*_PANEL_2K` / safe /
     button `Rect2`-константы из `scripts/ui_screens.gd` (и `pause_stats_menu.gd`)
     регуляркой `const\s+(\w+_2K)\s*:=\s*Rect2\(([\d.,\s]+)\)`. Альтернатива (надёжнее
     для ревью): сложить плоский словарь слотов прямо в скрипте, СВЕРЯя его с
     `ui_screens.gd` по комментарию-источнику, и падать с ошибкой, если размеры
     разошлись (anti-drift guard). Решение задокументировать в шапке скрипта.
   - **Маппинг слот → тип рамки.** Для каждого слота определить тип (`modal/panel/
     card/tooltip/hud_strip/field/button`) и взять соответствующие 9-slice бордюры из
     `UIThemePaths.MINIMAL_METAL_FRAME_TEXTURE_MARGINS`. Бордюры — НАТУРАЛЬНЫЕ (в
     пикселях исходника), при ином размере ассета они не скейлятся (орнамент рисуется
     в свой размер), тянется только плоская середина.
2. **Рисующее ядро.** Обобщить `render(w, h, kind, margins)` (взять из
   `tools/render_bright_frames.py`, не дублировать стиль — заимпортить/вынести общий
   модуль `tools/ui_frame_render.py`, если получится без поломки старых скриптов):
   - вход: целевой `w,h` слота @2K + тип + 9-slice бордюры;
   - орнамент (бордюр, угловые L-скобки, акценты, заклёпки) рисуется ТОЛЬКО внутри
     margin-полосы (left/top/right/bottom band), плоская середина — ровная заливка/
     градиент без деталей, чтобы тайл/стретч центра не искажал орнамент;
   - **никакого растяжения орнамента**: углы рисуются в нативном размере в каждом из 4
     углов; рёбра — повторяющийся/ровный паттерн в своей толщине; центр — флат.
3. **Размерная политика ассета.** Решить и зафиксировать в шапке: рисуем ли ассет ровно
   в `w×h` слота, ИЛИ в нативный размер источника с корректным соотношением бордюр/размер
   под этот слот. Рекомендация: рисовать в `w×h` слота @2K (точный размер, как требует
   тикет: «выдаёт ассеты точного размера»), бордюры — нативные → 9-slice ratio корректен
   по построению, рантайм потом юниформ-скейлит весь ассет под 1080p/4K (`stretch=keep`).
4. **Выход ассетов.** Складывать в новый подкаталог, не перетирая активную тему:
   `assets/sprites/ui/frames/overhaul_2k/` (или per-block: `.../overhaul_2k/menu_nav/`).
   Имя файла = `ui_frame_2k_<slot_slug>.png` (например `ui_frame_2k_qc_panel.png`).
   Перед записью — однократный бэкап существующих, если перетираем (паттерн
   `render_bright_frames.py`: `docs/design/backups/...`).
5. **Контактный лист-превью.** Сгенерить `docs/design/previews/ui_2k_frame_kit_contact.png`
   (как `build_preview()` в `build_ornate_ui_frame_kit.py`): сетка миниатюр с подписью
   slug + размер каждого ассета, для глазной проверки орнамента.
6. **Рендер-верификатор** (acceptance: «Ассеты проходят рендер-верификатор»). Отдельная
   функция/режим `--verify`, который по каждому ассету проверяет и печатает PASS/FAIL:
   - размер PNG == ожидаемый `w×h` слота (точный размер);
   - 9-slice валиден: `margin_left+margin_right < w` и `margin_top+margin_bottom < h`
     (центр существует);
   - **симуляция 9-slice** под несколько целевых размеров (1080p/2K/4K + сам слот):
     собрать выходное изображение из 9 кусков (углы — без масштаба, рёбра — тайл/стретч
     по одной оси, центр — по обеим) и убедиться, что углы попиксельно совпадают с
     оригинальными угловыми кусками (орнамент не исказился);
   - прогон через `tools/sprite_quality_audit.py`-логику (stray-острова/спеки/гало) —
     переиспользовать, не копировать;
   - safe-area внутри рамки пустая/прозрачная-под-контент (центр не «зашумлён»
     деталями орнамента).
   Exit code != 0 при любом FAIL (для CI/самопроверки).
7. **Документировать пайплайн.** В `docs/design/ui_screens_inventory.md` (секция

   гонять, куда падают ассеты, как читается verdict. Кратко — без раздувания.
8. **Самопроверка.** Прогнать скрипт + `--verify`, приложить путь к контактному листу и
   verdict в комментарий к тикету. Godot НЕ обязателен для генерации, но если есть —
   глазами свериться, что рамка в `_global_texture_style` не плывёт (опц.).

## Acceptance Criteria

- [ ] Скрипт `tools/build_ui_2k_frame_kit.py` принимает координаты @2K (из `*_2K`-констант

## Замечания / подводные камни

- **ANTI-COLLISION / locked paths.** `scripts/ui_screens.gd` — за Claude-контуром и
  массивно правится в эпике 2K (другие задачи блока). Эта задача — backend/integration,
  она ТОЛЬКО ЧИТАЕТ `ui_screens.gd` (парсит координаты) и НИЧЕГО в нём не пишет.
  `scripts/progression_data.gd` — тоже locked, к задаче отношения не имеет, не трогать.
  Все изменения этой задачи — в `tools/` + `assets/sprites/ui/frames/overhaul_2k/` +
  `docs/`. Это исключает конфликт правок с UI-исполнителями эпика.
- **Источник правды по размерам — координаты @2K, не легаси source-size.** Текущие PNG
  `minimal_metal` нарисованы под `MINIMAL_METAL_FRAME_SOURCE_SIZE` (786×716 и т.п.) — это
  НЕ размеры слотов @2K. Не путать: source-size = размер легаси-исходника; `*_PANEL_2K.size`
  = целевой размер слота, под который рисуем новый ассет. 9-slice бордюры берём из
  `MINIMAL_METAL_FRAME_TEXTURE_MARGINS` (они в нативных пикселях орнамента и остаются теми же).
- **Почему именно «точный размер слота» решает искажение.** Сейчас один `panel`-PNG
  (786×716) рантайм 9-slice'ит и под `QC_PANEL 600×340`, и под `PM_PANEL 898×820`, и под
  `FB_PANEL 940×780` — при сильно разном aspect центр растягивается неравномерно, а
  `_scaled_frame_margins_xy` скейлит бордюры раздельно по X/Y → орнамент плывёт. Рисуя
  ассет ровно в `w×h` слота с нативными бордюрами, мы фиксируем корректный 9-slice ratio
  по построению; рантайм потом юниформ-скейлит ассет целиком под 1080p/4K (`stretch=keep`),
  aspect сохраняется → орнамент не едет.
- **Детерминизм.** В рисовалке `render_bright_frames.py` нет `random`, а вот
  `generate_ui_overhaul_visual_assets.py` использует `random` для текстуры — если что-то
  оттуда заимствуется, ОБЯЗАТЕЛЬНО фиксировать сид, иначе повторный прогон даст другие
  пиксели и верификатор/диффы поплывут.
- **Edge-cases слотов.** Тултипы (`GT_*` 460×~140, `ST_*` 430×авто) имеют динамическую
  высоту (h по контенту) — для них генерить под шаблонную/максимальную высоту, бордюры
  считать корректными при любой реальной h ≥ (top+bottom margin). Кнопки (`*_BTN_*_2K`)
  — отдельный класс размеров (`220×72`, `240×72`, `280×60`, `260×64`, `380×104`), для них
  использовать button-margins (`MINIMAL_METAL_BUTTON_MARGINS`, ui_theme_paths.gd:298–314)
  и при желании отдельный режим, как `render_bright_buttons.py`.
- **Не перетирать активную тему без бэкапа.** `minimal_metal` — текущая боевая тема. Новые
  2K-ассеты класть в `overhaul_2k/`, интеграцию (подмену путей в `UIThemePaths`) выполнять
  ОТДЕЛЬНОЙ задачей эпика, не в этой (этот тикет = генерация + верификация пайплайна, шаг
  «интеграция» из формулы — это подключение путей, его можно сделать минимально или
  оставить под следующий тикет блока).
- **Связанные тикеты.** SCRUM-481 (эпик), SCRUM-484 (координатная спека блока Меню/Навигация
  — ВХОД этой задачи; см. `ui_screens_inventory.md:71`). Остальные блоки эпика (выбор героя/
  оружия, бой/HUD, экономика, кодекс, исходы) пойдут той же рисовалкой, когда их координаты
  будут зафиксированы — закладывать API скрипта расширяемым (словарь блок→слоты).
- **Стек.** Python 3 + Pillow (PIL) — уже используется во всех `tools/build_*`/`render_*`.
  Запуск из корня репо: `python3 tools/build_ui_2k_frame_kit.py` и `--verify`.
