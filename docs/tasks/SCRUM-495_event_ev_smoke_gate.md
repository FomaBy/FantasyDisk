# SCRUM-495: Балансный смоук-гейт на EV/ценность исходов событий

Jira: SCRUM-495 · Роль: QA · Контур: claude · Приоритет: P2 · foma · Эпик: SCRUM-476 (carry-over)
Статус: done (QA PASSED; PM sprint audit restored Jira Готово 2026-06-29)

## Что и зачем

Контекст — продолжение SCRUM-476 (BALANCE: «Награды событий должны быть достойны
риска/стоимости», уже закрыт). После EV-ребаланса исходов событий нет защиты от
регресса: будущая правка `scripts/event_data.gd` может молча вернуть перекос —
рискованная/платная опция станет давать награду слабее, чем безопасная в том же
событии. Игрок тогда теряет смысл рисковать (платить золотом/HP, идти в бой,
делать проверку) — выбор становится «ловушкой».

`tests/event_data_smoke_test.gd` сейчас валидирует только **структуру и границы
чисел** (валидные статы/типы боя, `heal_percent`/`health_percent_cost` в (0,1],
неотрицательные `money`/`cost_money`, мультипликаторы боя > 0). Соразмерность
награды риску/стоимости он **не проверяет**.

Цель: добавить в смоук **проверяемые EV/ценностные инварианты** — рискованная или
платная опция события не слабее по потенциальному апсайду, чем безопасная опция в
том же событии. Тест должен **падать** на искусственно заниженной награде рисковой
опции и **проходить** на текущих (ребалансированных) данных headless. Это
регресс-гейт, а не ребаланс — данные не трогаем, только тест.

## Текущее состояние в коде

### Данные событий — `scripts/event_data.gd`
- `RANDOM_EVENTS` (строки 3–115): массив из 12 событий. Каждое: `id`, `title`,
  `story`, `choices` (массив опций, ≥2).
- Каждая опция (choice) — словарь с полями-исходами. Поля, встречающиеся в данных:
  - **Стоимость/риск:** `cost_money` (плата золотом), `health_percent_cost`
    (плата % текущего HP), `risk: true` (флаг рискованной опции), `combat`
    (`{type, enemy_health_multiplier, money_multiplier, xp_multiplier}` — опция
    запускает бой), `check` (`{stat, difficulty}` + ветви `success`/`failure` —
    проверка характеристики, исход вероятностный).
  - **Награда:** `money` (золото), `stats` (`{stat_id: ±N}`), `mods`
    (мультипликаторы/флэты — баффы на забег: `attack_speed_multiplier`,
    `damage_multiplier`, `xp_gain_multiplier`, `summon_bonus`, `defense_flat`…),
    `heal_percent` (лечение % maxHP), `random_artifact: true` (случайный артефакт
    из reward_pool), `random_outcomes` (массив взаимоисключающих под-исходов),
    `post_combat` (`{stats, mods}` — награда ПОСЛЕ победы в бою).

### Как исход применяется — `scripts/ui_screens.gd` (locked path, читать не менять)
- `_resolve_event_choice_outcome` (5289–5305): сначала `random_outcomes` →
  случайный под-исход мержится в outcome; затем `check` → сравнение
  `stats[stat_id] >= difficulty`, ветвь `success`/`failure` мержится, ставится
  `check_passed`. То есть **исход события вероятностный** при наличии `check`/`random_outcomes`.
- `_apply_event_outcome_to_player` (5308–5333): порядок применения —
  `cost_money` (через `spend_money`, провал если не хватает золота → опция
  отменяется) → `money` → `reward` → `stats`/`mods`/`heal_percent` (через
  `apply_reward`) → `random_artifact` (через `reward_pool` + `_weighted_sample`)
  → `health_percent_cost` (минус % maxHP, не ниже 1).
- `_apply_event_choice` (5261–5286): если есть `combat` — запускает бой,
  `post_combat` кладётся в `game.pending_event_combat` и применяется после победы.

### Существующий тест — `tests/event_data_smoke_test.gd`
- `_initialize` (17–33): собирает `valid_stats` из `StatFormulas.BASE_STAT_ORDER`,
  гоняет `_check_events` и `_check_accessors`, на ошибках `push_error` + `quit(1)`,
  иначе `quit(0)`.
- `_check_outcome` (53–94): валидация одного блока исхода (stats/combat/числовые
  границы/`random_outcomes`/`heal_percent`/`post_combat`). **Числа проверяются на
  знак/диапазон, но НЕ на соразмерность.**
- `_check_events` (97–143): обход событий и опций; для `check` — валидность
  `stat`/`difficulty` и наличие ветвей `success`/`failure`; зовёт `_check_outcome`
  для choice и для веток. **Здесь нет сравнения опций между собой внутри события.**
- `_check_accessors` (146–173): `event_ids` / `event_by_id` / `pick_event`.

Вывод: гейт чисто структурный. Нужен новый слой — оценка «ценности» опции и
сравнение рисковой/платной vs безопасной в рамках одного события.

## Что сделать — по шагам

Работаем **только** в `tests/event_data_smoke_test.gd` (данные `event_data.gd` не меняем).

1. **Классификатор опции — `_choice_is_risky_or_paid(choice) -> bool`.**
   Опция считается рискованной/платной, если выполнено хоть одно:
   - `choice.has("risk")` и `choice["risk"] == true`;
   - `choice.has("combat")` (опция запускает бой);
   - `choice.has("cost_money")` и `cost_money > 0`;
   - `choice.has("health_percent_cost")` и `> 0`;
   - `choice.has("check")` (вероятностный исход — есть шанс провала с штрафом).
   Иначе опция «безопасная/бесплатная».

2. **Скоринг апсайда — `_choice_upside(choice) -> float`.**
   Считаем **потенциальный апсайд** (лучший достижимый исход опции, БЕЗ вычета
   стоимости — нас интересует «верх» награды за риск). Берём максимум по всем
   ветвям, которые опция может реализовать: для `check` — ветвь `success`; для
   `random_outcomes` — лучший под-исход (max по элементам); плюс `post_combat`
   (награда за победу) суммируется к `combat`-ветке. Очки за награду (фиксированные
   веса, задокументировать константами в тесте, например):
   - `money`: `+money * MONEY_W` (например `MONEY_W = 1.0` за 1 золото);
   - положительные `stats`: `+sum(max(0, v)) * STAT_W` (например `STAT_W = 25`);
   - положительные `mods`: мультипликатор `m>1` → `+(m-1)*100 * MOD_W`; флэт
     (`defense_flat`, `summon_bonus` и т.п. — складываемые, `m` не вокруг 1.0) →
     `+v * MOD_FLAT_W`; разнести по `_resolve_mod_value_kind` (см. ui_screens
     5628–5633: для `*_multiplier` — умножение, иначе сложение);
   - `heal_percent`: `+heal_percent * HEAL_W` (например `HEAL_W = 60`);
   - `random_artifact: true`: `+ARTIFACT_W` (например `ARTIFACT_W = 50`);
   - `combat.money_multiplier`/`xp_multiplier` > 1: `+(m-1)*100 * COMBAT_REWARD_W`.
   Веса подобрать так, чтобы на ТЕКУЩИХ данных тест проходил (см. шаг 5 — сначала
   прогнать, при необходимости подкрутить веса/смягчить инвариант, НЕ данные).
   Отрицательные `stats` в апсайд не идут (это штраф провала, а не награда).

3. **Инвариант на уровне события — `_check_event_ev(errors, event)`.**
   Для каждого события раздели опции на `risky` и `safe` по классификатору (шаг 1).
   Если в событии есть И рисковые, И безопасные опции:
   - `best_risky = max(_choice_upside) по risky`;
   - `best_safe  = max(_choice_upside) по safe`;
   - инвариант: `best_risky >= best_safe * SAFE_MARGIN` (например
     `SAFE_MARGIN = 1.0`; можно потребовать строгий перевес `>=1.0`, т.е. рисковая
     не слабее безопасной по апсайду). При нарушении — `errors.append(...)` с
     указанием `event.id`, обоими скорами и id опций.
   - Edge-case: если в событии все опции одной категории (нет пары risky+safe) —
     пропускаем (сравнивать не с чем), но это нормально (например `hot_spring`,
     `training_dummies`).

4. **Подключение в `_check_events`.** Внутри цикла по событиям (после текущих
   структурных проверок опций, ~строка 143) вызвать `_check_event_ev(errors, event)`.
   Не ломать существующий вывод/счётчик ошибок.

5. **Калибровка на текущих данных.** Прогнать тест headless (команда ниже). Он
   ДОЛЖЕН пройти на текущих `event_data.gd`. Если падает — подкрутить ВЕСА/MARGIN
   в тесте (не данные), либо ослабить инвариант до «рисковая опция не более чем на
   X% слабее безопасной» — но цель сохранить: явно платная/рисковая опция не должна
   проигрывать безопасной по апсайду. Зафиксировать финальные веса как именованные
   константы вверху файла с комментарием-обоснованием.

6. **Негативный само-тест (доказательство, что гейт ловит регресс).** Добавить в
   `_initialize` (или отдельной функцией) синтетическую проверку: сконструировать
   in-memory событие, где у рисковой опции (`risk:true` + `combat`) апсайд занижен
   (например только `money: 1`), а у безопасной — щедрый (`stats:{strength:2}` +
   `heal_percent: 0.5`), прогнать `_check_event_ev` на локальном `errors2` и
   убедиться, что он **вернул ошибку** (`assert errors2.size() > 0`). Если не
   вернул — это баг гейта, `push_error` + `quit(1)`. Так выполняется AC «тест падает
   на искусственно заниженной награде рисковой опции (проверено)» БЕЗ порчи реальных
   данных. Альтернатива (если проще): отдельный мини-скрипт-санити в комментарии —
   но предпочтительно встроенный негативный кейс.

7. **Прогон и зелёный гейт.**
   ```
   ~/Downloads/Godot.app/Contents/MacOS/Godot --headless --path . \
     --script res://tests/event_data_smoke_test.gd
   ```
   Должно вывести `Event data smoke test passed (N событий).` и `exit 0`.
   Также прогнать `tests/runtime_smoke_test.gd` (он тоже трогает события) — убедиться,
   что ничего не отвалилось.

## Замечания / подводные камни

- **Locked paths:** `scripts/ui_screens.gd` и `scripts/progression_data.gd` —
  anti-collision, только чтение. Эта задача их и не трогает — изменения строго в
  `tests/`. Diff обязан быть в одном файле.
- **Не ребаланс, а гейт.** Если инвариант падает на текущих данных — это сигнал
  калибровать ВЕСА теста, а НЕ менять `event_data.gd` (ребаланс уже сделан в
  SCRUM-476). Менять данные событий в рамках этой задачи запрещено.
- **Вероятностные исходы.** `check` и `random_outcomes` делают исход случайным.
  Для апсайда берём ЛУЧШУЮ достижимую ветвь (`success` / max по `random_outcomes`) —
  «потенциальный апсайд за риск», как и формулирует тикет («более высокий
  потенциальный апсайд»). Не пытаться считать строгий EV с вероятностями провала
  (вероятность зависит от рантайм-статов героя/сложности — в данных её нет).
- **`post_combat` — часть награды боевой опции:** при скоринге combat-ветки
  прибавлять `post_combat.stats`/`post_combat.mods` к её апсайду, иначе боевые
  опции (`defile`, `stand_ground`, `duel`, `fight_guardian`) недооценятся.
- **`mods` бывают двух родов:** мультипликаторы (`*_multiplier`, центр 1.0 — ценность
  `(m-1)`) и флэты (`defense_flat`, `summon_bonus` — складываемые, ценность = само
  значение). Разделять по суффиксу/ключу так же, как `ui_screens.gd` (5628–5633),
  иначе `summon_bonus: 1` или `defense_flat: 0.06` посчитаются неверно.
- **Не делать гейт «вакуумным».** Сохранить существующую защиту
  `RANDOM_EVENTS.size() < 5` (стр. 99–100). Новый инвариант не должен молча
  пропускать ВСЕ события (если ни в одном событии нет пары risky+safe — стоит
  заметить это, хотя бы информативным `print`, чтобы гейт не оказался no-op).
- **Подбор весов чувствителен** к смешанным наградам (золото vs стат vs артефакт vs
  бафф). Цель не «точный EV», а грубый, устойчивый порядок: рисковое ≥ безопасного.
  Лучше консервативный `SAFE_MARGIN` (1.0) и щедрые веса награды, чем хрупкий гейт,
  падающий от косметической правки.
- **Связанные:** SCRUM-476 (родитель, закрыт — ребаланс данных). Эпик SCRUM-214.
  Тест-партнёр — `tests/runtime_smoke_test.gd` (тоже гоняет события, держать зелёным).
- **Запуск Godot:** бинарь в `~/Downloads/Godot.app/Contents/MacOS/Godot` (4.6.3),
  всегда headless из корня репо (`--path .`).
